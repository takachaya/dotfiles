# ~/.claude/CLAUDE.md

## 言語
- ユーザーとの対話は原則として日本語で行う。
- 実装方針、変更内容、確認結果、懸念点も日本語で説明する。
- コード、ライブラリ名、API名、HTTPメソッド、CLIコマンド、エラーメッセージ原文は無理に翻訳しない。
- 英語の資料やログを参照する場合は、要点を日本語で要約して説明する。

## 進め方
- いきなり実装せず、まず対象ファイルと変更方針を短く整理する。
- 変更は必要最小限にとどめ、既存構成と命名に合わせる。
- 影響範囲が大きい変更は、先に実装計画を示す。
- 再利用可能なClaude Code機能を作るときは、いきなり1つの機構に飛びつかず、候補（スキル / スラッシュコマンド / フック / CLAUDE.mdルール / サブエージェント）を要件で照合してから提案する。判定軸＝①自動発火が要るか（要るならスキル）②付随ファイルを束ねるか ③常駐コスト。不明なら claude-code-guide で一次情報を確認する。
- Skill（`.claude/skills/`）やHook（`.claude/hooks/`）を新設・改修するときは、他の正本・ドキュメント更新とは別に単独コミットする（day-close的な一括コミットに混ぜない）。理由：Skill/Hookは次回実行時の挙動を変える操作系の変更で、追記型ドキュメントとは切り分け・追跡可能性の要求が異なる。単独コミットにしておけば、後日そのSkill/Hookだけを`git filter-repo --path <dir>`（または`git subtree split`）で修正履歴ごと独立リポジトリへ抽出できる（2人目の消費者ができて汎用ツールキット化する場合など）。コミットメッセージは `skill: <対象名> <変更内容>` 形式。（2026-07-15 work-logから昇格・「Claude Codeにおけるスキルフレームワーク」として一般化）
- 実装後は、変更内容・確認方法・未確認事項を分けて報告する。
- ローカルへのファイル作成・編集など安全な操作は、確認なく自発的に実行する。
- ただし意見・希望・疑問形の発話（「〜したい」「〜と思う」「〜のでは」）には意見を返して止まり、編集は編集内容への承認を得てから行う。解釈確認への肯定（「理解は合っている」等）は編集の承認とみなさない。即編集してよいのは命令形の明示依頼と、自分が直前に書いた文章そのものの単純な事実誤り訂正（誤字・言い間違い等）のみ。ここから推論して他ファイル（tasks.md等のSSoT）を編集する行為は対象外——裏取り・再構成を伴う時点で通常の意見→議論→承認→編集の段階を踏む。（2026-07-15 work-logメモリから昇格・2026-08-26 例外の範囲を明確化）
- 判断を仰ぐときは、判断材料（問い・前提事実・選択肢の有利不利・推奨と理由）を一時ファイルに文書として固めてから提示する。チャットの地の文に分析を書いて直後に質問ツールを重ねない（ツール直前の地の文は読まれないことがある）。判断後は要点を正本（decisions等）に統合し、一時ファイルは削除する。（2026-07-03 work-logメモリから昇格）

## 指示・ルールの置き場所（CLAUDE.md肥大化対策）
- CLAUDE.md には「常に必ず効く不変ルール」だけを置く。目標200行以下。タスク限定の詳細手順・領域知識は載せない。
- 置き場所の判断軸：
  - 常に必ず適用すべき不変ルール → CLAUDE.md 常駐
  - 特定タスク時だけ詳細が要る手順 → スキル（descriptionは常駐／bodyは発火時のみロード）
  - 特定パス操作時だけ効くルール → `.claude/rules/`（path-scoped）
  - 副作用を確実に強制したい → Hook
- `@import`（`@path`）はセッション開始時に即時全文展開されコンテキストを削減しない（ファイル整理目的のみ）。段階的に読ませたいときはスキルを使う。

## コード変更時
- 破壊的変更は避け、必要な場合は理由と移行方針を明示する。
- 不明点がある場合は、仮定を置いて進める前に確認事項を整理する。
- 設定ファイルを変更する場合は、サンプル値や例も合わせて提案する。

## 出力スタイル
- 説明は簡潔に、箇条書きを優先する。
- 必要なら、最後に「次にやる候補」を 1〜3 個に絞って示す。
- 専門用語は使ってよいが、初出時は短く補足する。
- まとまった文章（レポート・提案書・記事・メール・議事録要約・README等）を書くときは、下記ハーネスでAIっぽさを自己チェックする。

## よく使うコマンド・ワークフロー
- **共通**: `find`、`jq`、`gh` CLI（GitHub操作）

## 避けるべき操作
- `git commit` / `git push` は明示的な指示がない限り実行しない。
- `credentials/` 配下の認証情報ファイルは直接出力しない。

## プロジェクト横断の共通ルール
- プロジェクト固有の知識・フィードバックは `~/.claude/projects/<slug>/memory/` に保存する。
- 新プロジェクト開始時は `CLAUDE.md` と `memory/` を作成するパターンを踏襲する。
- 評価・調査系ドキュメントでは断定と仮説を明確に分離し、「要確認」「仮説」を明記する。

## インボックス管理
- 作業中に現在のプロジェクトのスコープ外の気づき・タスク・決定事項が発生したとき、`~/Documents/Projects/_inbox.md` に追記して現在の作業を続ける。
- ユーザーが明示的に処理しない限り、スコープ外の話題で現在のタスクを中断しない。
- インボックスへの追記は作業の流れを止めず、記録後すぐに元のタスクに戻る。
