# 引き継ぎプロンプト生成（ハンドオフ）

ハブ&スポーク運用（work-log ⇔ 実体リポ）や長いセッションの分割で、文脈を別セッションへ渡すための定型出力。受け手のセッションは**この会話を読めない**前提で書く。

**入力源は2通り**: ①現セッションの内容（従来） ②タスク管理ファイル上の1タスク（例: work-log `tasks.md` のタスクを指定され「これを起動プロンプト化して」）。②では該当タスクの next・申し送り・関連リンク先から生成し、末尾に起動コマンド（`cd <対象リポ> && claude "<プロンプト>"`）を添える。対象リポにハブとの接点ファイル（`_worklog-bridge.md` 等）があれば、申し送りの確認先・報告先として成果物・完了条件の節に含める。

## 出力構造（この順・過不足なく）

1. **冒頭1文**: 何を・どこまでやってほしいか（完了状態を含める）。
2. **## 確定済みの前提（編集判断はこれに従う／再検討しない）**: 決定済み事項を箇条書き。各項目に**出典**（ファイルパス・decisions の日付・URL）を付ける。受け手が蒸し返さないための節。
3. **## 現在のステータス**: 対応済み／未対応を明確に分ける。
4. **## やること**: 番号付き。対象ファイルはパスで具体的に。
5. **## 作業ルール・制約**: 対象リポの規範（例: スライドは4層モデル・一方向依存）、`git commit/push` の可否、やらないこと（スコープ外）。
6. **## 成果物・完了条件**: 何ができたら完了か。ハブへ戻す報告の形式（「何を反映したか1行で返す」等）もここに。
7. **## 要確認（潰せるものは潰す）**: 未確定事項。**未回答の質問を確定事項として書かない**。

## 規範

- **自己完結性**: セッション内の略語・コードネーム・「さっきの件」を展開する。受け手が追加質問なしで着手できるかを出力前に自己チェック。
- **確定と未確定を混ぜない**: ユーザーがまだ答えていない論点は「要確認」へ。勝手に仮定で確定させない。
- 顧客の個人情報・社外秘・認証情報は含めない（組織コンプライアンス準拠）。
- 出力はチャット本文が基本。ファイル保存・tasks への申し送り転記は指示されたときのみ（work-log の申し送り記法はプロジェクト側 CLAUDE.md に従う）。
