# テスト駆動開発（TDD）

TDD は Red → Green のループ。このスキルは、そのループが「残す価値のあるテスト」を生むための参照資料：良いテストとは何か、テストをどこに書くか、アンチパターン、ループの規則。全セクションが毎サイクルに適用される — ループの前と最中に参照する（後からではない）。

コードベースを探索するとき、`CONTEXT.md` があれば読み、テスト名やインターフェースの語彙をプロジェクトのドメイン言語に合わせる。触る領域に ADR があれば尊重する。

## 良いテストとは

テストは公開インターフェースを通じて振る舞いを検証する。実装詳細は見ない。コードが全面的に変わってもテストは変わらないのが理想。良いテストは仕様書のように読める —「user can checkout with valid cart」はどんな能力が存在するかを正確に伝える — し、内部構造に依存しないためリファクタを生き延びる。

例は [tests.md](tests.md)、モックの指針は [mocking.md](mocking.md) を参照。

## シーム — テストを書く場所

**シーム（seam）**とは、テストの対象とする公開境界のこと：内部に手を突っ込まずに振る舞いを観測できるインターフェース。テストはシームに置き、内部構造に対しては書かない。

**事前に合意したシームでのみテストする。** テストを書く前に、対象とするシームを列挙してユーザーに確認する（確認は AskUserQuestion で行う）。未確認のシームにテストを書かない。すべてはテストできない — シームを先に合意することで、テストの労力を網羅的なエッジケースではなくクリティカルパスと複雑なロジックに集中させる。

問いかけ：「公開インターフェースは何か？どのシームをテストすべきか？」

## アンチパターン

- **実装結合** — 内部コラボレータをモックする、private メソッドをテストする、サイドチャネルで検証する（インターフェースを使わず DB を直接クエリする等）。兆候：振る舞いは変わっていないのにリファクタでテストが壊れる。
- **トートロジー** — 期待値をコードと同じやり方で再計算している（`expect(add(a, b)).toBe(a + b)`、同じ手順で手作りしたスナップショット、定数同士の比較）。構造上必ずパスし、コードと食い違うことができない。期待値は独立した情報源から取る — 既知の正しいリテラル、手計算した例、仕様。
- **水平スライス** — 全テストを先に書いてから全実装をする。まとめて書いたテストは「想像上の」振る舞いを検証してしまう：ユーザーに見える振る舞いではなく形をテストし、実際の変更に鈍感になり、実装を理解する前にテスト構造にコミットしてしまう。代わりに**垂直スライス**で進める — 1テスト → 1実装 → 繰り返し。各テストは前サイクルの学びに反応する**トレーサーバレット（tracer bullet）**。

## ループの規則

- **Red before Green。** 失敗するテストを先に書き、それをパスさせる最小限のコードだけを書く。将来のテストを先取りしない。投機的な機能を足さない。
- **1サイクル1スライス。** 1シーム・1テスト・1最小実装。
- **リファクタリングはループの一部ではない。** レビュー段階（`/code-review` スキル）に属する。Red → Green の実装サイクルには含めない。
