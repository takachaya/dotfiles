ADR（Architecture Decision Records）を「腐らせない」ために、以下の運用ルールを厳守して管理する。

## ディレクトリ構成

```
docs/adr/
├── latest/                 # 現行版。各ADRは一つだけ。
│   └── NNNN-{slug}.md
└── archive/                # 旧版を番号ごとのサブディレクトリで保管。
    └── NNNN/
        └── {slug}-YYYYMMDD.md
```

- `latest/` には「いま生きている決定」だけを置く。
- 冷めた決定（旧版）は必ず `archive/` によける。
- **番号 `NNNN` は絶対に振り直さない**（決定の履歴を追えるようにするため）。4桁ゼロ埋め（例: `0007`）。

## 依頼の分類

ユーザーの依頼を必ず次の3つに分類する。

- **A. 新規追加**: 新しいADRを起こす。`latest/` の最大番号の次を発番。
- **B. 更新（archive送り → 新版を latest へ）**: 意思決定としての変更がある場合。旧版を `archive/NNNN/{旧slug}-{YYYYMMDD}.md` に退避してから新版を書く。
- **C. 上書き（archive送りなし）**: typo・てにをは・言い回しの調整など、意思決定としての変更がない修正。`Edit` で書き換えるだけ。

## 既存ADRに手を入れるとき（最重要）

既存ADRの編集依頼を受けたら、**編集を開始する前に必ずユーザーに「更新（B）か上書き（C）か」を `AskUserQuestion` で尋ねる**。

理由: 意思決定の変更でない修正まで archive 送りにすると、アーカイブがノイズで溜まる。アーカイブは「過去の意思決定」を残す場所であり、修正履歴置き場ではない。ノイズが溜まると認知負荷が上がり、メンテナンス性が下がる。

判断はユーザーに委ねるが、下表に基づく推奨を選択肢の先頭に「（推奨）」付きで提示すること。

| 変更内容 | 推奨 |
| --- | --- |
| typo・てにをは・改行調整 | 上書き（C） |
| 言い回しの改善、説明の追記（決定は不変） | 上書き（C） |
| 技術スタックの追加・削除・差し替え | 更新（B） |
| データモデルのフィールド追加・削除・型変更 | 更新（B） |
| ステータス変更（Accepted → Superseded など） | 更新（B） |

## 操作手順

### A. 新規追加
1. `docs/adr/latest/` 内の既存ファイルから最大番号を調べ、+1 して4桁ゼロ埋めで発番する（空なら `0001`）。
2. slug は決定内容を表す英小文字ケバブケースにする。
3. `docs/adr/latest/NNNN-{slug}.md` を後述のテンプレートで作成する。

### B. 更新
1. 旧版 `docs/adr/latest/NNNN-{旧slug}.md` を `docs/adr/archive/NNNN/{旧slug}-{YYYYMMDD}.md` に移動する（`archive/NNNN/` がなければ作成）。
2. 日付は `date +%Y%m%d` で取得した当日を使う。
3. 同じ番号 `NNNN` で新版を `docs/adr/latest/` に書く（番号は変えない、slug は変えてよい）。
4. ステータス変更を伴う場合は、新旧の関係（Superseded by / Supersedes）を本文に記す。

### C. 上書き
1. archive 送りはしない。
2. `latest/NNNN-{slug}.md` を `Edit` で直接修正する。

## ADRテンプレート

```markdown
# NNNN. {タイトル}

- ステータス: Accepted | Superseded | Deprecated
- 日付: YYYY-MM-DD

## コンテキスト
（なぜこの決定が必要になったか。背景・制約・前提）

## 決定
（何を選んだか。具体的に）

## 結果
（この決定によって生じる良い影響・悪い影響・トレードオフ）
```
